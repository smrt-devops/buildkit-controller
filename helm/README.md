# buildkit-controller Helm chart

One chart, `helm/buildkit-controller`. It installs the CRD (`crds/`, generated by
`cargo xtask crdgen`), one Deployment running every role (API, mTLS edge,
reconciler; default 2 replicas, one leader), the config file as a ConfigMap, a
Service (API and edge ports), Gateway API routes to that Service, a ClusterIP
metrics Service, least-privilege RBAC, a PodDisruptionBudget and, optionally, a
ServiceMonitor and BuildKitPools.

```
helm install bk helm/buildkit-controller -n buildkit-system --create-namespace \
  --set edge.endpoint=tcp://bk.example.com:8444 --set edge.serverName=bk.example.com \
  --set-json 'gateway.api.parentRefs=[{"name":"bk","namespace":"gateway-system","sectionName":"api"}]' \
  --set-json 'gateway.edge.parentRefs=[{"name":"bk","namespace":"gateway-system","sectionName":"edge"}]' \
  --set 'auth.oidc[0].url=https://token.actions.githubusercontent.com' \
  --set 'auth.oidc[0].audiences={buildkit-controller}'
```

`edge.endpoint` and `edge.serverName` are required, and so is `gateway.parentRefs`
unless `service.type` is `LoadBalancer` or `gateway.enabled` is `false`. The chart ships no OIDC issuer, so without `auth.oidc` only ServiceAccount tokens
authenticate. `values.schema.json` validates values.

## Exposure

Clients reach two ports: the API (HTTPS, 8443 on the Service) and the edge (mTLS,
8444). The chart exposes them through a Gateway by default. A LoadBalancer Service
is the alternative.

### Gateway API (default)

The Service is ClusterIP, and the chart attaches routes to a Gateway you already run.
It renders upstream `gateway.networking.k8s.io/v1` kinds only:

| Route | Kind | Gateway listener it needs | In the standard channel since |
|---|---|---|---|
| API, `gateway.api.mode: terminate` (default) | `HTTPRoute` and `BackendTLSPolicy` | `HTTPS`, `tls.mode: Terminate` | HTTPRoute v1.0.0, BackendTLSPolicy v1.4.0 |
| API, `gateway.api.mode: passthrough` | `TLSRoute` | `TLS`, `tls.mode: Passthrough` | v1.5.0 |
| Edge | `TLSRoute` | `TLS`, `tls.mode: Passthrough` | v1.5.0 |

So the default needs the Gateway API v1.5.0 or later standard-channel CRDs and an
implementation that supports both kinds. The chart checks `.Capabilities.APIVersions`
and skips a route whose kinds the cluster does not serve; NOTES.txt then names the
missing kinds. With `helm template`, pass them, for example
`--api-versions gateway.networking.k8s.io/v1/TLSRoute`.

The edge is always TLS passthrough. The controller authenticates each build by its
client certificate, which a gateway that terminates TLS would never forward, so the
chart has no option to terminate the edge. The TLSRoute matches the SNI
`edge.serverName`, plus `*.<edge.allocationDomain>` when that is set. Point those DNS
names at the Gateway, and set `edge.endpoint` to the address and port of its TLS
listener.

The API has two modes:

- `terminate` (default). The Gateway terminates TLS with its own certificate and the
  `BackendTLSPolicy` makes it re-encrypt to the controller, checking the serving
  certificate against `gateway.api.backendTLS.hostname` (default `edge.serverName`,
  which every serving certificate covers) and the CA bundle ConfigMap the controller
  maintains (`<fullname>-ca-bundle`, key `ca.crt`). With a publicly trusted
  certificate on the Gateway, clients need no CA: leave out the Action's `ca-cert`
  and the recipe's `API_CA`. With a public `edge.tls.secretName`, set
  `gateway.api.backendTLS.wellKnownCACertificates: System`, or list its CA in
  `caCertificateRefs`.
- `passthrough`. A TLSRoute on a passthrough listener; clients see the controller's
  serving certificate, as with a LoadBalancer. Use it where the implementation lacks
  BackendTLSPolicy or HTTPRoute timeouts. The API TLSRoute and the edge TLSRoute
  match the same SNI, so give them different listeners with `gateway.api.parentRefs`
  and `gateway.edge.parentRefs` (`sectionName`).

Give each route its listener with `sectionName`: `gateway.api.parentRefs` for the
HTTPS listener and `gateway.edge.parentRefs` for the TLS passthrough listener. A
parentRef without `sectionName` (or `port`) attaches the HTTPRoute to every HTTP and
HTTPS listener of that Gateway that admits it. On a shared Gateway with a plain HTTP
listener, the API, and the bearer tokens clients send it, would then also be served in
cleartext, so NOTES.txt warns about it. `gateway.parentRefs` is the default for both
routes when the per-route lists are empty. In passthrough mode the chart fails to
render when both TLSRoutes could match the same SNI on the same listener.

An Envoy Gateway example. The API is on 443 with a publicly trusted certificate, and
the edge on 8444:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: {name: bk, namespace: gateway-system}
spec:
  gatewayClassName: eg
  listeners:
    - name: api
      protocol: HTTPS
      port: 443
      hostname: bk.example.com
      tls: {mode: Terminate, certificateRefs: [{name: bk-example-com}]}
      allowedRoutes:
        namespaces: {from: Selector, selector: {matchLabels: {kubernetes.io/metadata.name: buildkit-system}}}
    - name: edge
      protocol: TLS
      port: 8444
      hostname: bk.example.com
      tls: {mode: Passthrough}
      allowedRoutes:
        namespaces: {from: Selector, selector: {matchLabels: {kubernetes.io/metadata.name: buildkit-system}}}
```

```yaml
edge: {endpoint: "tcp://bk.example.com:8444", serverName: bk.example.com}
gateway:
  api: {parentRefs: [{name: bk, namespace: gateway-system, sectionName: api}]}
  edge: {parentRefs: [{name: bk, namespace: gateway-system, sectionName: edge}]}
  envoy: {enabled: true}   # optional, see below
```

The API URL is then `https://bk.example.com`. `cargo xtask e2e` runs this setup
(Envoy Gateway v1.9.3, Gateway API v1.6.1 standard channel) on kind.

Implementations whose Gateway API v1.5 or v1.6 conformance reports pass the
`GATEWAY-TLS` profile, which is TLSRoute passthrough: agentgateway, Calico, Cilium,
Envoy Gateway, Istio, kgateway, Kong Operator, NGINX Gateway Fabric, Portus and
Traefik. Kong Operator does not report BackendTLSPolicy, and NGINX Gateway Fabric and
Traefik do not report HTTPRoute request timeouts; on those, use
`gateway.api.mode: passthrough`. GKE's managed Gateway and the AWS Load Balancer
Controller report no TLSRoute support, so on them use the LoadBalancer Service. The
reports are under
[conformance/reports](https://github.com/kubernetes-sigs/gateway-api/tree/main/conformance/reports)
in the Gateway API repository.

#### Timeouts

A queued allocation request is silent until a worker is free: up to the pool's
`allocation.maxQueueTimeout` plus `workers.startTimeout` plus 10 s, which is 12m10s
with default pool settings. The HTTPRoute sets `timeouts.request` and
`timeouts.backendRequest` to `gateway.api.timeouts` (15m); raise both when a pool
allows longer waits (at most 1h + 30m + 10 s). Check the Gateway's own idle
timeouts too. Envoy Gateway derives the route's idle timeout from the request
timeout unless a ClientTrafficPolicy on the Gateway sets `streamIdleTimeout`;
`gateway.envoy.enabled` covers that case. TLSRoutes carry no timeout fields: the
gateway's TCP idle timeout applies, which in Envoy is 1 hour by default, and the
controller's TCP keepalives (after 30 s idle, then every 10 s) keep the connection
active on paths that count them.

#### Per-address caps behind a gateway

The controller caps work per client address: `edge.maxHandshakesPerIp` (32 TLS
handshakes in progress), `api.maxConnectionsPerIp` (128 open API connections) and
`auth.serviceAccount.maxReviewsPerIp` (4 TokenReviews in flight). Behind a gateway
the controller sees the gateway's pod addresses, not the clients', so all clients
share each cap. Turn on PROXY protocol so the controller reads the client address
from the gateway: `api.proxyProtocol` and `edge.proxyProtocol` with `trustedCIDRs` set
to the gateway's source addresses (the gateway pods as /32s, or a range only the
gateway uses, never the pod CIDR), plus `gateway.envoy.proxyProtocol: true` on Envoy
Gateway. Only connections from `trustedCIDRs` are parsed, and each must carry a v2
header. The trust model is in
[docs/operations.md](../docs/operations.md#proxy-protocol). Without PROXY protocol,
raise the caps to the number of jobs that can start at once, or set them to 0 to turn
them off, and enforce per-client limits at the gateway instead.

#### Implementation extras

`gateway.envoy.enabled` renders an Envoy Gateway `BackendTrafficPolicy` for each
route: TCP keepalive and a connect timeout, and on the HTTPRoute a `streamIdleTimeout`
equal to `gateway.api.timeouts.request`. With `gateway.envoy.proxyProtocol: true` it
also sets `proxyProtocol: {version: V2}` on the route of each listener whose
`proxyProtocol` is enabled. It needs the `gateway.envoyproxy.io/v1alpha1` CRDs.
For other implementations, put their policy objects in `gateway.extraManifests`.
Each entry is an object or a string, and both go through `tpl`.

### LoadBalancer

Set `service.type: LoadBalancer` to expose both ports on the Service directly, with
no Gateway and no `gateway.parentRefs`. Use it where the managed gateway has no TLS
passthrough. The controller then serves its own certificate on the API too, so
clients need its CA unless `edge.tls.secretName` is publicly trusted.
`externalTrafficPolicy: Local` (the default) keeps client addresses, which the
per-address caps count. Raise the load balancer's idle timeout as described in
[Load balancer idle timeout](#load-balancer-idle-timeout).

### In-cluster only

`gateway.enabled: false` with the default ClusterIP Service exposes nothing outside
the cluster, for example for `BuildKitClaim` users or a port-forward on kind.

## Requirements

The build sandbox depends on these cluster settings. Without an enforcing CNI or the IPv6 cluster ranges, pools still report Ready while builds are not isolated or have no IPv6 egress. A Pod Security refusal shows as `Degraded` with reason `PodCreateFailed`.

- The cluster's CNI must enforce NetworkPolicy. The worker sandbox is a NetworkPolicy. kindnet
  and the default EKS VPC CNI ignore it, and on them a build reaches every pod and the cloud
  metadata endpoint.
- Each pool namespace must admit privileged pods under Pod Security Admission. Label it
  `pod-security.kubernetes.io/enforce=privileged`. Rootless BuildKit needs unconfined seccomp
  and AppArmor, which `baseline` and `restricted` refuse. Without the label the pool reports
  `Degraded` with reason `PodCreateFailed` and the PodSecurity error.
- Give each pool its own namespace, with no other workloads or NetworkPolicies, and never the
  release namespace, which holds the CA Secret. NetworkPolicies add up, so another policy that
  selects the worker pods widens the sandbox.
- List the cluster's IPv6 pod, service and node ranges in `workerNetwork.clusterCIDRs`, plus
  any IPv4 pod or node ranges outside RFC 1918 and 100.64.0.0/10. Until it holds an IPv6
  range, workers get no IPv6 egress, so on an IPv6-only cluster image pulls fail. Listing
  every pod, service and node range there also stops a pool's `allowCIDRs` from opening
  them; `workerNetwork.permittedCIDRs` lists the exceptions (see docs/operations.md, Worker
  egress).

## Load balancer idle timeout

This applies to `service.type: LoadBalancer`, and to the load balancer in front of a
Gateway. A queued allocation request is silent for up to 12m10s with default pool
timeouts, and builds can be quiet for long steps. TCP keepalive keeps most
paths open. For a load balancer that ignores keepalives, raise its idle timeout
above that bound, with `service.annotations` for the chart's Service or on the
Gateway's own Service.

| Cloud | Annotation |
|---|---|
| AWS (NLB, AWS Load Balancer Controller) | `service.beta.kubernetes.io/aws-load-balancer-listener-attributes.TCP-8443: tcp.idle_timeout.seconds=900` and `service.beta.kubernetes.io/aws-load-balancer-listener-attributes.TCP-8444: tcp.idle_timeout.seconds=900` (per listener; use your `service.ports.api` and `service.ports.edge`; 60-6000 s). The in-tree NLB has no such annotation.[^aws-nlb] |
| AWS (classic ELB, in-tree) | `service.beta.kubernetes.io/aws-load-balancer-connection-idle-timeout: "900"` (seconds)[^aws-elb] |
| Azure | `service.beta.kubernetes.io/azure-load-balancer-tcp-idle-timeout: "30"` (minutes, 4-100)[^azure] |
| GCP (passthrough network LB) | none; connection-tracking entries expire 60 s after the last packet and the value can't be changed, so TCP keepalive must fire more often than every 60 s (the controller's default probes after 30 s idle, then every 10 s)[^gcp] |

[^aws-nlb]: AWS Load Balancer Controller, `listener-attributes`: https://github.com/kubernetes-sigs/aws-load-balancer-controller/blob/main/docs/guide/service/annotations.md#listener-attributes ; range: https://docs.aws.amazon.com/elasticloadbalancing/latest/network/update-idle-timeout.html
[^aws-elb]: https://github.com/kubernetes/cloud-provider-aws/blob/master/pkg/providers/v1/aws.go (`ServiceAnnotationLoadBalancerConnectionIdleTimeout`); https://docs.aws.amazon.com/elasticloadbalancing/latest/classic/config-idle-timeout.html
[^azure]: https://github.com/kubernetes-sigs/cloud-provider-azure/blob/master/pkg/provider/azure_loadbalancer.go (idle timeout bounds 4 and 100 minutes)
[^gcp]: https://cloud.google.com/load-balancing/docs/network/ext-netlb-traffic-distribution ("Idle timeout")

## Tests

`cargo xtask helm-test` lints and compares `helm template` output with the
goldens in `xtask/fixtures/helm-test` (`--update` rewrites them) and checks that
invalid values are rejected. `cargo xtask helm-verify` installs the chart on a
throwaway kind cluster in LoadBalancer mode and applies a pool after the
controller is Ready. `cargo xtask e2e` runs the Gateway exposure on Envoy Gateway.
