# Dashboards

Four Grafana dashboards in [`examples/grafana`](../examples/grafana) cover the controller and the cache registry. They read Prometheus only and use the metrics listed in the [metrics reference](metrics.md).

| Dashboard | Use it to |
|---|---|
| BuildKit overview | Check that the controller is healthy: replicas, leader, CA, certificate expiry, reconcile loop, Kubernetes watches. |
| BuildKit pools and allocations | See pool size against its ceiling and floor, the claim queue, allocation latency, build duration and why workers are retired. |
| BuildKit edge and API | See client connections to the edge, API traffic and latency, login checks and OIDC key fetches. |
| BuildKit build cache | See cache requests, the hit ratio, store size against its budget, garbage collection and denials. |

Each dashboard has a Data source variable, and the namespace and pool variables list the pools from `buildkit_pool_max`. Every panel has a description that says what it shows and what to do about it. Hover the `i` in the panel's corner to read it, or see the [panel tables](#panels) below.

## Scraping

Prometheus must scrape both metrics Services, because the cache panels read the registry pod and everything else reads the controller replicas.

| Service | Port | What it serves |
|---|---|---|
| `<fullname>-metrics` | `metrics` | Controller replicas. Only the leader exports the pool and claim gauges. |
| `<fullname>-registry` | `metrics` | The cache registry pod. |

With the default naming the Services are `buildkit-controller-metrics` and `buildkit-controller-registry`. With the Prometheus Operator, `metrics.serviceMonitor.enabled` creates one ServiceMonitor that selects both. Without it, add a scrape job for each Service. Do not add your own scrape of the registry Service next to the chart's ServiceMonitor, or its series are collected twice.

Both pods export `buildkit_watch_errors_total` and `buildkit_watch_namespace_unlisted`. The dashboards sum or take the maximum over pods for every panel, so a query holds whichever pods are scraped.

## Import

Pick one.

**Grafana UI.** In Grafana choose Dashboards, New, Import, upload one file from `examples/grafana`, and pick your Prometheus data source. Repeat for each file.

**Provisioning file.** Copy the four JSON files to a directory Grafana can read and point a provider at it:

```yaml
# /etc/grafana/provisioning/dashboards/buildkit.yaml
apiVersion: 1
providers:
  - name: buildkit
    folder: BuildKit
    type: file
    allowUiUpdates: false
    options:
      path: /var/lib/grafana/dashboards/buildkit
```

**Sidecar ConfigMap.** With the Grafana Helm chart's dashboard sidecar, load the files into a ConfigMap carrying the label the sidecar watches (`grafana_dashboard` by default):

```bash
kubectl create configmap buildkit-dashboards -n monitoring --from-file=examples/grafana/
kubectl label configmap buildkit-dashboards -n monitoring grafana_dashboard=1
```

The sidecar picks them up without a restart. Set `sidecar.dashboards.label` in the Grafana values if your sidecar watches another label.

## Use cases

### Capacity against scaling.max

Open the pools dashboard and look at Allocated workers against scaling.max and at Utilisation. A pool that sits near 1 at its busy hours and shows Claims waiting above 0 needs a higher `scaling.max`, if the nodes can take it. Check that the claims that wait end as `ok` in Queue wait. If many end as `timeout`, callers already give up. Build duration shows how long each worker is held, so `scaling.max` times 3600, divided by that p50 in seconds, is the builds per hour the pool can finish. A pool that never passes 0.2 has a ceiling higher than it needs.

### Cold starts and warm pool sizing

Warm and cold binds shows how often a claim found a ready worker. Allocation latency by path gives the price of a cold bind: it is your worker start time. If cold binds are common in the busy hours, raise `scaling.minWarm`, or add a schedule window with a higher floor for those hours, and watch Warm workers against the desired floor. Warm well above the floor all day is spare capacity you can give back. Warm below the floor with many Starting pods means workers are slow to become ready: look at image pulls and node capacity before you raise the floor again.

### Queue timeouts

A claim that ran out of queue time ends as `pool_exhausted` in Allocation outcomes and as `timeout` in Queue wait. Match the time of the first timeout with Claims waiting and Allocated workers against scaling.max. At the ceiling, the pool is too small for the burst. Under it, workers start too slowly: see cold starts above.

### Cache effectiveness and budget

On the cache dashboard, Manifest hit ratio and Hit ratio over time say how often a build found its cache. Expect a dip when a branch or base image first builds. A low ratio that lasts means builds do not share a cache key, or entries are evicted before they are reused: compare it with Garbage collection. Set the Cache budget variable to `cache.maxSize` in bytes. If Store used against the budget stays above 0.9 and evictions with `budget="volume"` run all day, raise `cache.maxSize`. Evictions with `budget="pool"` mean one pool exceeds its share. Denied pushes are normal for untrusted builds. Denied pulls are not.

### Certificate expiry

The overview shows the days left on each certificate kind. The edge certificates renew themselves. The client CA and the internal CA do not: rotate them before the soonest expiry panel nears 0, using [CA rotation](operations.md#ca-rotation). Certificate load errors and CA replacements that are not `missing` mean the CA Secret was edited or restored from a backup.

### Triage after a failover

When Leaders on the overview was 0 for a while, the leader changed, or a rollout restarted the replicas, work through these in order. Check that Leaders is 1 again and that Leader changes in 1 hour has stopped growing. Check Kubernetes watch errors and Namespaces a watch cannot list for watches that did not recover. Check Reconcile passes for errors that stop after the new leader starts.
